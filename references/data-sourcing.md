## 二、Wind 调用写法

### 单日分位数（唯一正确写法）

```
get_index_fundamentals
question: 查询 931024.CSI 在 2026-10-16 的市盈率PE(TTM)及其近10年分位数
```

返回一行，含六个关键字段：

| 字段 | 用途 |
|---|---|
| 市盈率 | 当日 PE(TTM) |
| 市盈率序号 / 市盈率最大序号 | 前者是当日 PE 在样本里的排名，后者是样本总长度 |
| 分位数 | **直接就是温度，0–100**，不用自己算 |

分位数 = 序号 ÷ 最大序号 × 100。用它来判断样本是否够长：最大序号 < 500 说明该指数 PE 历史不足两年，分位数不稳，别计入均值。

### 行情快照（可批量）

```
get_index_price_indicators
windcode: "801010.SI,801030.SI,801080.SI"
indexes: "最新交易日,中文简称,最新成交价,涨跌幅,年初至今涨跌幅,市盈率(TTM)"
```

一次传多个代码，省调用。但**分位数不能这样批量拿**。

### K 线（取 924 基准价）

> 注：2024-09-24 的收盘价已固化在 `scripts/targets.py`（每标的 base 列），**日常更新不再取 kline**；仅当新增标的、需要补其 924 基准时才用下面写法。

```
get_index_kline
windcode: 931024.CSI
begin_date: 2024-09-20  end_date: 2024-09-26  period: "10"
```

`period` 是字符串："10" 日 K，"11" 周 K，"12" 月 K。返回里 `MATCH` 字段是收盘价。

## 三、三条不能碰的坑

### 1. 区间查询会系统性偏高 15–27 度

把 question 写成「查询沪深300在2016-2025年每年末的PE分位数」时，Wind 走的是另一套算法（区间内重算分位），结果和单日查询差异巨大，且区间超过 100 行会被截断。

实测对照（A股整体温度，单日查询值）：2016-12-30 = 55.14、2018-12-28 = 8.45、2022-09-30 = 28.03、2024-06-28 = 24.40、2024-09-30 = 43.87、2026-10-16 = 51.55。区间查询出来的数会比这些高一大截。

**结论：1776 次单日查询就老实查，别想批量。**

### 2. 分位数偶尔会抖

同一条序列里，某个日期的「市盈率最大序号」突然变小（比如前后是 952 → 490 → 1071），说明那次返回用的样本集不同，分位数会失真。

实例：2021-12-31 的 931024.CSI 返回 22.55%，但它的 PE 8.41 低于 2021-09-30 的 8.49（0.53%）且高于 2022-03-31 的 8.12（0.75%），真实分位应在 0.6 附近。**遇到这种，用相邻两点的 PE 线性插值修正**，别直接采信，否则曲线上会凭空鼓一个包。

### 3. 新指数会被钉死在 0 或 100

指数刚发布时 PE 历史只有几十天，当日 PE 很容易是这段时间的最高或最低，分位数直接给 100 或 0。

阈值取法：
- 宽松（页面早期用法）：不足 120 个交易日不计入
- 严谨：不足 500 个交易日不计入

用哪个要一致，并在图注里写明。港股曲线目前用 500 天，所以港股通非银从 2020-12-31（样本 770 天）才开始进入均值。

## 四、落盘

每取一个点就写入历史库，不要攒在对话里。会话记录不保存工具返回的原始值，中途断了只能全部重取——这件事发生过一次，重跑了整条港股曲线。

历史温度统一存在 `data/temperature-history.json`，用 `scripts/history.js` 管理：

```bash
node scripts/history.js add  data/temperature-history.json a 2026-11-30 52.31 37
node scripts/history.js stat data/temperature-history.json
```

当期快照（44 个标的的涨跌幅/PE/温度）是一次性的，不进历史库——它每天变，存下来没有复用价值。只有**采样点的温度**值得攒，因为十年走势要靠它。

历史库的价值随时间增长：存到第三年，你就有了十三年的序列；删了就从 2016 年重新爬。换机器、备份时优先带走 `data/` 目录。
